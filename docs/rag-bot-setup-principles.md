# Корневые принципы настройки RAG-чатбота (любая платформа, любая ниша)

> Универсальные правила. Применимо к Flynn, b24u, GPTs, Custom GPT, любому self-hosted LLM-стеку. Не привязано к недвижимости, e-commerce, услугам — любой каталог/база знаний.

## Контекст применения

RAG-чатбот = LLM + retrieval из базы знаний (RAG) + системный промпт. Типичная задача: отвечать на вопросы пользователей про каталог товаров/услуг/объектов, цитируя живые карточки.

Этот документ — про **где лежит логика поведения** и **как тестировать**. Это не про конкретные платформы и не про тюнинг моделей.

---

## Принцип 1. Разделение «правила vs данные»

| В системный промпт | В базу знаний (RAG) |
|---|---|
| **Правила поведения.** Как обрабатывать класс запросов: подбор, фильтр, count, расплывчатый, fallback. | **Факты клиента.** Адреса, цены, характеристики, контакты, описания. |
| **Структура ответа.** Формат строки, порядок секций, тон, запреты. | **Каталоги / готовые ссылки.** Slice-URL для типовых выборок. |
| **Алгоритм разбора запроса.** Какие параметры извлекать из реплики, как сочетать. | **Терминологические соответствия.** «X на сайте = Y в речи клиента» — только факт, без инструкций. |

**Почему так:** системный промпт **всегда** в контексте LLM. RAG-карточка попадает в контекст только если ranker поднял её в Top-N. Если правило поведения зависит от того, найдёт ли RAG нужную карточку — оно ломается в случайные моменты.

## Принцип 2. Структура, не формулировки

В правилах описывай запрос **по структуре извлекаемых параметров**, не списком фраз-триггеров.

**Антипаттерн:**
```
Если агент пишет «что есть», «какие варианты», «покажи варианты», «ассортимент»,
«что у вас», «что в наличии», «что подобрать» — выдай подборку.
```
Этот список бесконечен. Любая новая формулировка («что у тебя есть?», с эмодзи, опечатка) — fallback.

**Правильно:**
```
Если в запросе указан только один структурный параметр (категория ИЛИ бюджет ИЛИ
бренд, без сочетания) — это «расплывчатый» класс. Действие: slice-URL каталога с
этим параметром, без подбора конкретных карточек.
```
LLM сама извлекает параметры из любой формулировки.

## Принцип 3. Тесты на классах запросов, не на строках

Регрессия должна проверять **структурные классы**, каждый в 3+ лексических вариантах.

**Антипаттерн:** жёсткие assertion «бот должен ответить именно так на эту фразу».

**Правильно:** для класса «один критерий — бюджет» прогнать запросы вида:
- «до 5000»
- «бюджет 5000 рублей»
- «варианты до пяти тысяч»

Если хотя бы один FAIL — проблема в покрытии класса промптом, не в RAG-карточке.

## Принцип 4. Лимиты UI обходятся, если мешают

Многие платформы (Flynn — 4000 знаков на промпт) дают UI-лимиты. Это часто **только UI**, БД лимита не имеет. Если упёрся — выйди на REST/SQL уровень, не сжимай правила и не выноси их в KB.

Признак, что выносить НЕ надо: если правило про «как себя вести», оно должно быть в промпте, чего бы это ни стоило.

## Принцип 5. Backend-fallback ≠ ошибка модели

Многие платформы при «низкой релевантности RAG» возвращают захардкоженный шаблон («оставьте контакт, менеджер свяжется»). Это срабатывает **до** системного промпта и не редактируется из UI.

Признаки:
- Ответ цитируется в **двойных кавычках** (бот не сгенерировал, скопировал).
- Срабатывает только на запросы, где RAG вернул мало/ничего.
- Не реагирует на правки промпта.

Лечится **только** тем, что промпт корректно отрабатывает все структурные классы — и не оставляет места для пустой RAG-выдачи. Пример: запрос «1-комн» (один критерий — категория). Если в промпте есть правило «один критерий → slice-URL каталога», промпт сразу формирует ответ из СПРАВОЧНИКА без обращения к RAG-офферам. Backend-fallback не срабатывает, потому что бот уже сгенерировал валидный ответ.

---

## Структура системного промпта (универсальный шаблон)

```
## РОЛЬ И ТОН
<КТО — целевая аудитория, B2B/B2C/внутренний>
<ОБРАЩЕНИЕ — на «вы» / «ты»>
<ТОН — деловой / дружелюбный / экспертный>
<ЗАПРЕТЫ ТОНА — без эпитетов, без продающих манипуляций, без формализма>

## ИСТОЧНИКИ В КОНТЕКСТЕ
Опиши типы записей, которые приходят с RAG:
- ОБЪЕКТЫ — конкретные карточки (ID, URL, основные параметры).
- КАТАЛОГИ — записи со slice-URL (фильтры на каталог-страницу).
- СПРАВОЧНЫЕ — описания компании, условия, FAQ.

Что цитировать дословно (URL, ID, цены) и что не выдумывать (адреса вне СПРАВОЧНИКА, контакты).

## ЛОГИКА ОТВЕТА — РАЗБЕРИ ЗАПРОС НА ПАРАМЕТРЫ

Извлекай из реплики параметры. Перечисли свои — например:
- категория (тип товара)
- размер/тариф/комплектация
- цена/бюджет
- бренд/модель/линейка
- атрибут (цвет, материал, отделка, особенность)
- тип запроса (подбор, конкретный объект, фото/планировка, «сколько», условия, общее)

### Правила по комбинациям параметров

A) Полная конкретика: категория + типоразмер + бюджет/цена.
→ 2-3 объекта в бюджете строкой <шаблон>. В конце один slice-URL с фильтрами.
Если в бюджете 0 — ближайшие по лесенке ±N%, помечать отклонение.

B) Конкретный объект (по ID/артикулу/точному параметру).
→ Полная карточка с URL. Дополнительные ссылки (фото, спецификация) если есть.

C) Запрос медиа (фото/планировка/видео).
→ Найти карточку по параметру → ссылка дословно. Иначе fallback к каталогу.

D) ОДИН КРИТЕРИЙ (только бюджет, только категория, только бренд, только размер).
→ НЕ подбирать случайные объекты. Дать slice-URL каталога с этим фильтром.
   - Если параметр работает на портале URL-фильтром — собрать URL.
   - Если нет (например, площадь без фильтр-параметра) — 2-3 примера + предложить уточнить.
Slice-URL не зависит от Top-N RAG, закрывает любую выборку.

E) Парные комбинации (категория + бюджет, бренд + категория, …).
→ Один slice-URL с обоими фильтрами + диапазон цен из СПРАВОЧНИКА.

F) «Сколько / количество».
→ Точное число НЕ называть (Top-N RAG неполный, бот считает только что видит).
→ Slice-URL с фильтром + 2-3 примера-объекта.

G) Доменные специфичные правила.
→ Условия покупки/доставки/гарантии → ссылка на запись «Условия».
→ Переадресация к человеку (комиссия, договор, бронь) → стандартная формула.

## ЗАПРЕТЫ
- Не уходи в "нет данных" при наличии объектов по основным параметрам.
- Не выдавай случайные объекты на запрос с одним критерием.
- Не подменяй конкретный объект каталог-ссылкой, если объект есть.
- Не выдумывай URL, ID, цены, факты.
- Не повторяй чужие шаблоны в кавычках.

## СПРАВОЧНИК
<Таблицы данных, не правил>:
- ID/категории/маппинг
- Адреса/контакты/реквизиты
- Диапазоны цен по типам
- Формула slice-URL и доступные значения параметров

## ФОРМАТ ОТВЕТА
1. Одно вводное предложение по сути запроса.
2. Список (объекты или каталог-ссылки), каждая строка с URL.
3. Для одного критерия — только slice-URL без объектов.
URL — голым текстом, не markdown.
```

### Что НЕ должно быть в промпте

- Списки синонимов триггер-фраз.
- Готовые шаблоны ответов на конкретные формулировки.
- Длинные тематические описания (это в KB).
- Бесконечные few-shot примеры (1-2 максимум, для иллюстрации формата).

---

## Структура KB (универсальная)

KB — только **данные клиента**. Каждая карточка короткая и точечная.

| Категория | Содержание | Размер |
|---|---|---|
| «О компании» | 1 запись. Что делает, основные категории, ключевое отличие. | 400-800 |
| «Условия / тарифы / гарантии» | 1-2 записи. Способы оплаты, доставка, возврат. | 300-700 |
| «Контакты» | 1 запись. Кто, телефоны/мессенджеры, что можно публиковать. | 200-400 |
| «Каталоги» | По 1 короткой записи на категорию: название + URL. | 50-150 |
| «Готовые slice-URL» | Топ-10 типичных пар «фраза → URL». Только пары, без правил. | 50-100 |
| «Терминологические разрывы» | Если внутренний термин ≠ речи клиента. Только факт. | 100-300 |

### Что НЕ должно быть в KB

- Карточки с правилами поведения («НЕ уходи в "нет данных"», «выдай 3 примера»).
- Карточки со списками синонимов триггер-фраз.
- Карточки с готовыми шаблонами ответов.
- Длинные карточки (>1000 знаков) — вытесняют объекты из Top-N RAG.

## Регрессия — структурные классы

Минимум 6 классов, каждый в 3 лексических вариантах = 18 тестов.

| Класс | Что проверяем | Шаблон формулировки |
|---|---|---|
| **A. Полная конкретика** | Подбор по всем параметрам | `<категория> <типоразмер> до <бюджет>` |
| **B. Конкретный объект** | Запрос по ID/артикулу | `расскажи про <ID>` / `артикул <X>` |
| **C. Один критерий — категория** | Только категория | `<категория>` |
| **D. Один критерий — бюджет** | Только бюджет | `до <X>` / `бюджет <X>` |
| **E. Атрибут-фильтр** | С нестандартным атрибутом | `<категория> с <атрибут>` |
| **F. Count-запрос** | «Сколько / количество» | `сколько <категория> <атрибут>` |

Каждый класс — 3 лексических варианта (с/без пунктуации, с/без вежливости, перефразировки, опечатки).

### Симптомы провала

- Ответ цитирован в `"двойных кавычках"` (backend-fallback платформы).
- Текст «оставьте контакт», «свяжется с вами», «к менеджеру» — без URL.
- Нет URL на запрос, где данные есть.
- Выдуманные URL/цены/факты (галлюцинации).
- Точное число на count-запросе (обычно врёт).
- Ответ короткий («да», «нет») — отказ от подбора.

### Допустимые FAIL

- Class F (count) — частично, потому что Top-N RAG физически не показывает полный фид. Промпт правильно отвечает «дам каталог + примеры», но клиент мог хотеть число.
- Backend-fallback платформы на запросах, где данные физически отсутствуют (1 раз из 18) — это норма.

## Антипаттерны (что НЕ делать)

### Антипаттерн 1. «Лечить формулировки KB-карточкой синонимов»

**Как выглядит:**
> Создаю KB-карточку: «Если агент пишет “что есть”, “какие варианты”, “ассортимент”, “что у вас”, “покажи” — выдай каталог + 3 примера».

**Почему плохо:**
- Список синонимов конечен, формулировок бесконечно.
- Карточка попадает в Top-N RAG не на всех запросах — правило применяется через раз.
- Появляется на демо хорошо, ломается на первой новой фразе.

**Как правильно:** правило «один критерий → slice-URL» в системном промпте, без перечня фраз.

### Антипаттерн 2. «Лечить count-запрос KB-карточкой с готовым числом»

**Как выглядит:**
> Создаю KB: «На вопрос “сколько X” отвечай: их 37».

**Почему плохо:**
- Число устаревает с каждым ребилдом фида.
- Бот цитирует устаревшее число, агент верит.

**Как правильно:** правило в промпте «точное число НЕ называй, дай slice-URL и 2-3 примера». Slice-URL открывается клиентом — там актуальное число.

### Антипаттерн 3. «KB как замена промпта»

**Как выглядит:**
> Промпт в UI ограничен 4000 знаков, не помещается. Вынес 3 правила в KB-карточки длиной по 1500 знаков.

**Почему плохо:**
- KB-карточки конкурируют с офферами за Top-N RAG. Длинные правила-карточки вытесняют объекты.
- Правила применяются нестабильно.

**Как правильно:** обойти UI-лимит через REST/SQL уровень платформы. Если совсем нельзя — сократить правила до самых критичных, но всё равно в промпт.

### Антипаттерн 4. «Готовые шаблоны ответов в промпте/KB»

**Как выглядит:**
> В промпте раздел «ПРИМЕРЫ»: 8 длинных few-shot с готовыми ответами слово в слово.

**Почему плохо:**
- LLM копирует шаблон, не адаптируя под запрос.
- На любой запрос вне примеров — ступор или fallback.

**Как правильно:** 1-2 коротких примера для иллюстрации формата строки. Не для «как ответить на конкретный вопрос».

### Антипаттерн 5. «Тесты как assertion на точную фразу»

**Как выглядит:**
> Тест: `assert(response.includes('По 1-комн Острова до 25 млн: 1-комн 47.9 м²...'))`.

**Почему плохо:**
- LLM генерирует свой текст, тест ломается от пунктуации.
- Не проверяет логику, проверяет совпадение фраз.

**Как правильно:** `assert(response.has_url AND response.contains_one_of(['1-комн', '47.9']) AND not response.has('оставьте контакт'))`. Проверять структурные свойства ответа, не точный текст.

## Чек-лист настройки нового бота с нуля

1. **Собрать данные клиента:** каталоги (URL+ID), прайсы (диапазоны), адреса/контакты, условия покупки.
2. **Понять, что фильтруется через URL-параметры портала.** Это определяет, какие slice-URL бот может собирать.
3. **Заполнить шаблон системного промпта** (3500-4500 знаков). Все правила здесь.
4. **Создать минимальную KB:** О компании, Условия, Контакты, Каталоги — по 1 короткой записи. Готовые slice-URL для топ-10 запросов.
5. **Прогнать структурную регрессию** (18 тестов из 6 классов).
6. **На FAIL: разобраться, какой класс провалился, и поправить правило в промпте.** Не добавлять KB-карточки с синонимами.
7. **Демо-страница** клиенту — простой HTML с виджет-скриптом.
8. **Через 1-3 дня живого использования: аудит истории сообщений.** Найти провалы из реальных диалогов, отнести к структурным классам, доработать промпт.

---

## Чек-лист исправления существующего бота (если настроен по антипаттерну)

1. **Snapshot текущего состояния** (промпт + все KB-карточки).
2. **Прогон baseline-регрессии** (18 структурных тестов) — измерить, сколько провалов до правок.
3. **Удалить из KB:** карточки с правилами, синонимами, готовыми шаблонами ответов.
4. **Переписать промпт** на структурную логику по шаблону выше.
5. **Если правил много (>4000 знаков), а UI лимитирует** — выгрузить промпт через REST/SQL платформы.
6. **Очистить кеш RAG/индекса** (если есть кнопка).
7. **Прогрев** — отправить любой запрос, чтобы индекс перестроился.
8. **Повторный прогон регрессии.** Цель — сокращение провалов на 50%+.
9. **Финальный отчёт клиенту** — что было, что стало, какие классы запросов теперь работают.

## Когда даже правильный промпт + правильная KB не помогают: LLM bottleneck

Если после всех правильных настроек (правила в промпте, данные в KB, структурные тесты зелёные) бот всё равно:
- выдумывает атрибуты (площадь / цену / номер)
- даёт URL, ведущий на другую квартиру
- цитирует CRM-id вместо реальных полей

— это значит **слабая LLM в стеке платформы**, не баг настройки.

Подтверждение:
1. Сверить ответы бота с фидом — `flynn-verify-bot-citations.mjs` или аналог.
2. Сверить выдумки с реальностью — есть ли в фиде вообще такая квартира?
3. Прогнать те же запросы через детерминированный код по фиду (`answer-from-feed.mjs` как референс).
4. Если простой код отвечает правильно, а LLM — нет, дело **не в данных**.

В этой ситуации варианты:
- Попросить платформу сменить модель (если есть выбор тарифа).
- Свой backend-proxy: виджет встраиваешь свой, запросы парсишь сам, RAG-поиск делаешь сам, потом передаёшь сильной LLM (Claude/GPT-4o) с жёсткими константами в промпте «цитируй только из переданных карточек».
- Принять как есть с дисклеймером.

Реальный кейс (Fizika 2026-05-24): см. `clients/fizika/findings-llm-hallucination-2026-05-24.md`. Flynn-LLM галлюцинирует ~10-15% ответов, на 10 провальных запросах 200-строчный детерминированный скрипт даёт 10/10 корректных ответов.

## Когда метод не работает

Если после переписывания по принципам провалы остались на 30%+ структурных тестов — корень не в настройке, а в одном из:
- Платформа физически не индексирует часть данных (например, не парсит YML-поля). Лечится правкой фида/импорта.
- Backend-fallback платформы агрессивный, срабатывает даже на нормальные ответы. Лечится только обращением к команде платформы.
- Модель LLM слабая (не Claude 4.6+, не GPT-5). Лечится сменой плана/платформы.
- Данные клиента противоречивы или неполны. Лечится наведением порядка в источнике данных, не настройкой бота.
