# Промпт для исправления Flynn-бота (любого клиента)

> Самодостаточная инструкция. Скопируй её целиком в чат с LLM-агентом (Claude/ChatGPT), который имеет доступ к браузеру через MCP-Playwright или к API Flynn через curl. Под одного клиента — один прогон.

---

## Контекст

Платформа Flynn (flynn-ai.ru) — кабинет на Supabase. Боты на ней часто настраивают по **антипаттерну**: правила поведения пихают в KB-карточки как «синонимические списки» и «шаблоны ответов», вместо того чтобы держать их в системном промпте. Это работает на демо, но ломается на любой новой формулировке.

Цель прогона: переписать одного клиента с антипаттерна на правильную структуру.

## Принципы

1. **Логика — в системный промпт. Данные — в KB.** Правило «как обрабатывать класс запросов» = промпт. Факт «адрес ЖК X», «slice-URL для Y» = KB.
2. **Структура, не формулировки.** В правилах описывать структуру запроса (какие параметры указаны — комната / бюджет / категория / атрибут), не списки фраз-триггеров.
3. **Промпт всегда в контексте, KB зависит от RAG-ranker.** Правило не должно зависеть от того, попадёт ли карточка в Top-N.
4. **UI-лимит 4000 знаков на промпт обходится через PostgREST.** Это не повод сжимать правила и переносить их в KB.
5. **Тесты на классах, не на строках.** Каждый структурный класс запросов проверять 3+ лексическими вариантами (с/без пунктуации, с/без вежливости, с синонимами).

## Шаг 1. Диагностика (сначала измерить, потом чинить)

### 1.1. Скачать текущее состояние
```bash
curl 'https://flynn-ai.ru/rest/v1/widget_settings?select=system_prompt&project_id=eq.<PROJECT_ID>' \
  -H "apikey: $APIKEY" -H "Authorization: Bearer $TOKEN" > prompt-before.json

curl 'https://flynn-ai.ru/rest/v1/training_data?select=*&project_id=eq.<PROJECT_ID>' \
  -H "apikey: $APIKEY" -H "Authorization: Bearer $TOKEN" > kb-before.json
```
**Сохрани оба файла** — это твой rollback на случай провала.

### 1.2. Признаки антипаттерна в текущем боте

Посмотри `kb-before.json`. Бот настроен по антипаттерну, если есть **хотя бы 2 из 4**:

- KB-карточки со словами «синонимы», «если агент пишет X — выдай Y», «триггеры».
- KB-карточки с перечислением вариантов фразы запроса («что есть = варианты = ассортимент = …»).
- Длинные KB-карточки (>500 знаков), содержащие правила поведения («НЕ уходи в "нет данных"», «выдай N примеров»).
- Промпт <2000 знаков с короткими правилами + 5+ длинных KB-карточек с инструкциями.

Если бот «правильный»: правила в промпте подробные (3000+ знаков), KB короткая (только данные/факты).

### 1.3. Прогнать структурный аудит

Через `widget-chat` API клиента (`api_key` из `projects`):
```bash
curl -X POST 'https://yngogqokndrgmyhidxor.supabase.co/functions/v1/widget-chat' \
  -H 'Content-Type: application/json' \
  -d '{"api_key":"<API_KEY>","messages":[{"role":"user","content":"<ЗАПРОС>"}],"visitor_id":"audit-001"}'
```

Прогнать **минимум 15 запросов из 6 классов**. Адаптируй под домен клиента (недвижимость → товары / услуги / еда / отели). Каждый класс — 3 формулировки:

| Класс | Что проверяем | Примеры (адаптировать под клиента) |
|---|---|---|
| **A. Полная конкретика** | Подбор по всем критериям | «двушки Talento до 40 млн», «красные кроссовки 42 размер до 5000» |
| **B. Конкретный товар** | Запрос по ID/артикулу | «расскажи про лот 480573», «артикул SKU-1234» |
| **C. Один критерий — категория** | Только категория | «двушки», «кроссовки», «пиццы» |
| **D. Один критерий — бюджет** | Только бюджет | «до 40 млн», «до 5000», «дешёвое» |
| **E. Атрибут-фильтр** | С нестандартным атрибутом | «с отделкой», «водонепроницаемые», «без глютена» |
| **F. Count-запрос** | «Сколько» | «сколько 1-комн до 30», «сколько моделей кроссовок» |

Симптом провала — любое из:
- Ответ в **двойных кавычках** (backend-fallback Flynn, цитирует шаблон).
- Содержит «Оставьте контакт», «свяжется с вами».
- Нет URL/конкретики на запрос, где данные есть.
- Выдуманные URL/цены/факты.
- Точное число на count-запросе (обычно врёт).

### 1.4. Зафиксировать baseline

В файл `audit-baseline-<клиент>.md`:
- Сколько KB-карточек, сколько из них — антипаттерн (правила/синонимы).
- Длина промпта.
- Из 15 структурных тестов — X прошло, Y провалилось. По каждому FAIL — какой класс и какая формулировка.

Это твоя точка отсчёта. После исправлений будет с чем сравнить.

## Шаг 2. Эталонный системный промпт (шаблон)

Шаблон ниже — каркас. Заполни секции под клиента. Цель — описать **логику по структуре запроса**, не перечень триггеров. Длина ~3500–4500 знаков, обходит UI-лимит через PostgREST PATCH.

```
## РОЛЬ И ТОН
<КТО — например: «B2B-консультант компании X для агентов / B2C-помощник магазина Y»>.
<ОБРАЩЕНИЕ — на «вы» или «ты»>.
<ТОН — деловой / дружелюбный / экспертный>.
<ЗАПРЕТЫ — без эпитетов, без продающих вопросов в конце, без формализма>.

## ИСТОЧНИКИ В КОНТЕКСТЕ
Опиши типы данных, которые будут приходить с RAG:
- ОФФЕРЫ / ТОВАРЫ — карточки конкретных объектов (с ID и URL).
- КАТАЛОГИ — записи со slice-URL (с фильтрами).
- СПРАВОЧНЫЕ — описания компании, условия, FAQ.

URL и ID цитируй дословно. <Доменные ограничения — например: адреса только из СПРАВОЧНИКА, ставки банков не называй>.

## ЛОГИКА ОТВЕТА — РАЗБЕРИ ЗАПРОС НА ПАРАМЕТРЫ

Определи, какие параметры указаны:
- <ПАРАМЕТР_1 — например: ЖК / категория / бренд>
- <ПАРАМЕТР_2 — комнатность / размер / тип>
- <ПАРАМЕТР_3 — бюджет / цена>
- <ПАРАМЕТР_4 — размер / площадь / вес>
- <ПАРАМЕТР_5 — атрибут / отделка / цвет / материал>
- ТИП ЗАПРОСА: подбор / конкретный лот / планировка/фото / «сколько» / общий

### Правила по комбинациям параметров

A) Полная конкретика (категория + типоразмер + бюджет/площадь):
Подбор 2–3 объектов в бюджете. Формат строки: «<ШАБЛОН — например: тип, м², ЖК, цена, № — URL>». В конце slice-URL.
Если в бюджете 0 — близкие по лесенке ±3% → ±5% → ±10%, помечай каждое отклонение. «Нет» — только при пустом ±10%.

B) Конкретный объект (по ID или точному параметру):
Полная карточка одной строкой с URL. <Если применимо — URL фото/планировки>.

C) Запрос фото/планировки:
Карточка ±5% по параметру → «<Подпись>: URL». Иначе — «<нет данных>, каталог: URL категории».

D) ОДИН КРИТЕРИЙ — не подбирай случайные офферы. Дай slice-URL каталога:
- Только бюджет → каталог-URL по всем категориям с ?<фильтр-бюджет>.
- Только категория → каталог-URL с ?<фильтр-категория>.
- Только атрибут (бренд/цвет) → каталог-URL с ?<фильтр-атрибут>.
- Только размер/площадь → 2–3 примера из контекста + предложи уточнить категорию.
Slice-URL покрывает любую выборку и не зависит от Top-N RAG.

E) Категория + бюджет (без типоразмера):
Один slice-URL с двумя фильтрами + диапазоны цен по типам.

F) Запрос «сколько / количество»:
Точное число НЕ называй (Top-N RAG неполный). Slice-URL + 2–3 примера.
С атрибутом-фильтром — проверь объекты по основной категории; есть — выдай примеры с пометкой фактического атрибута; «нет» — только при 0 объектов в категории.

G) Доменные правила:
<СПЕЦИФИЧНЫЕ — например: условия покупки → запись «Условия», ставки → к менеджеру; гарантия → запись «Гарантия»; контакты → запись «Контакты»>.

## ЗАПРЕТЫ
- Не уходи в "нет данных" при наличии объектов по основным параметрам (категория, бренд).
- Не выдавай 2–3 случайных оффера на запрос с одним критерием (используй slice-URL).
- Не подменяй конкретный объект каталог-ссылкой, если объект есть.
- Не выдумывай URL, ID, цены, факты.

## СПРАВОЧНИК
<Таблицы данных — НЕ правил>:
- ID каталога: <категория_1>=<id>, <категория_2>=<id>, ...
- АДРЕСА / КОНТАКТЫ / РЕКВИЗИТЫ: <данные>
- Цены / диапазоны / характеристики: <данные>
- Формула slice-URL: https://<domain>/catalog/<id>/?<param1>=<val>&<param2>=<val>
  Значения <param1>: ...
  Значения <param2>: ...

## ФОРМАТ ОТВЕТА
1. Одно вводное предложение по сути запроса.
2. Список (объекты или каталог-ссылки), каждая строка заканчивается URL.
3. Для одного критерия — только slice-URL, без случайных объектов.
URL — голым текстом (https://...), не markdown.
```

### Что НЕ должно быть в промпте

- Списки синонимов («что есть = варианты = ассортимент»).
- Готовые шаблоны ответов на конкретные фразы.
- Бесконечные few-shot примеры (1–2 максимум, для иллюстрации формата).
- Дублирование данных, которые лучше держать в KB (длинные описания, прайсы).

## Шаг 3. Эталонная KB (что должно быть)

KB — только **данные клиента**. Каждая карточка коротка и точечна.

| Категория карточки | Содержание | Размер |
|---|---|---|
| **«О компании»** | 1 запись. Что делает, основные продукты/категории, ключевые отличия. | 400–800 знаков |
| **«Условия покупки / тарифы / гарантии»** | 1–2 записи. Способы оплаты, доставка, гарантия, возврат. | 300–700 знаков |
| **«Контакты»** | 1 запись. Кто, телефоны, мессенджеры (если можно публиковать). | 200–400 знаков |
| **«Каталоги»** | По 1 короткой записи на категорию: название + URL. | 50–150 знаков |
| **«Готовые slice-URL»** | Для топ-10 типичных запросов: «<категория> до <бюджет>» = URL. Только пары «фраза → URL», без правил. | 50–100 знаков |
| **«Терминологические разрывы»** | Если в данных используется внутренний термин, отличный от того, что говорят клиенты. Только факт «X на сайте = Y в речи клиента». **Без инструкций боту, без синонимов.** | 100–300 знаков |

### Что НЕ должно быть в KB

- Карточки с правилами поведения («НЕ уходи в "нет данных"», «выдай 2-3 примера»).
- Карточки со списками синонимов («что есть = варианты = …»).
- Карточки с готовыми шаблонами ответов на конкретные формулировки.
- Карточки длиной >1000 знаков (разбить, длинные вытесняют офферы из Top-N).

## Шаг 4. Применение исправлений

### 4.1. Удалить антипаттерн-карточки

Для каждой карточки из `kb-before.json`, которая попадает под «что НЕ должно быть»:
```bash
curl -X DELETE 'https://flynn-ai.ru/rest/v1/training_data?id=eq.<KB_ID>' \
  -H "apikey: $APIKEY" -H "Authorization: Bearer $TOKEN"
```

### 4.2. Добавить недостающие KB-карточки

Каждую — отдельным POST:
```bash
curl -X POST 'https://flynn-ai.ru/rest/v1/training_data' \
  -H "apikey: $APIKEY" -H "Authorization: Bearer $TOKEN" \
  -H "Content-Type: application/json" \
  -d '{"project_id":"<PROJECT_ID>","type":"text","content":"<содержание короткое, только данные>"}'
```

### 4.3. Записать новый системный промпт (обход UI-лимита 4000)

```bash
curl -X PATCH 'https://flynn-ai.ru/rest/v1/widget_settings?project_id=eq.<PROJECT_ID>' \
  -H "apikey: $APIKEY" -H "Authorization: Bearer $TOKEN" \
  -H "Content-Type: application/json" \
  -H "Prefer: return=representation" \
  -d '{"system_prompt":"<полный текст промпта по шаблону>"}'
```

### 4.4. Очистить кеш индекса

В кабинете Flynn → Обучение ИИ → База знаний → **Очистить кеш**. Через API кнопки нет (известное ограничение).

### 4.5. Прогреть индекс

Один любой запрос через widget-chat API — баннер «Индекс прогревается» исчезнет после первого успешного ответа.

## Шаг 5. Регрессия

Прогнать те же 15 запросов из Шага 1.3. Цель — структурные классы PASS. Допустимо FAIL только на классе F (count) — это backend-ограничение Flynn, не лечится из кабинета.

**ВАЖНО про ответный кеш Flynn:** запросы кешируются по точной строке. Если перепрогоняешь те же формулировки сразу после правки — попадёшь в старый кеш. Используй версии с `?` на конце или перефразируй.

## Шаг 6. Финальный отчёт

В `audit-after-<клиент>.md`:
- Длина нового промпта.
- Сколько KB-карточек удалено / добавлено / переписано.
- Результат: было X/15, стало Y/15. По FAIL — какой класс и почему не закрылся (что зависит от Flynn-команды).

## Шаг 7. Передать клиенту

Дай клиенту короткое описание изменений (без технических деталей):
- «Бот стал понимать общие вопросы (только бюджет / только категория) — раньше уходил в "оставьте контакт"».
- «Перестал выдумывать данные и врать с числами на запросах "сколько"».
- «Точнее соответствует формулировкам, отличным от тестовых сценариев».

И дай новую демо-ссылку.

## FAQ (часто всплывает при настройке)

**Q: Бот всё равно возвращает «оставьте контакт» после правок.**
A: Backend-fallback Flynn, не лечится из кабинета. Подавляется тем, что промпт правильно отрабатывает структурные классы и не оставляет места для пустой RAG-выдачи. Если на конкретной формулировке fallback — это говорит, что какой-то класс запросов не покрыт логикой промпта.

**Q: На «сколько X в Y» бот выдумывает число.**
A: Top-N RAG ≠ полный фид. Не лечится. Только правило в промпте «точное число НЕ называй, дай slice-URL и 2-3 примера».

**Q: Длина промпта 4500 знаков, в UI поле обрезается на 4000.**
A: PATCH через PostgREST принимает больше (Шаг 4.3). Клиент потом не сможет редактировать промпт руками в UI — это плата за расширенную логику.

**Q: KB-карточки с готовыми slice-URL — это норм или антипаттерн?**
A: Короткие (50-150 знаков, пара «фраза → URL») — норм, это данные. Длинные (с правилами «когда применять») — антипаттерн, выноси правила в промпт.

**Q: Демо-ссылка для клиента?**
A: HTML-страница с одной строкой `<script src="https://flynn-ai.ru/widget-proxy/widget-script?key=<API_KEY>"></script>`. Заливается на любой статический хостинг (gh-pages, FTP).

**Q: История диалогов клиента?**
A: Кабинет Flynn → Сообщения. Или дамп через `curl 'https://flynn-ai.ru/rest/v1/messages?select=*&project_id=eq.<PROJECT_ID>&order=created_at.desc&limit=500'`.
